# Bug hunt — 2026-11-14

This is a focused audit of the authority, signed recorder, thermal model,
assembly and browser flows, not a proof that the project is bug-free.
Regression coverage is included with the changes; the local acceptance command
is `./scripts/gate.sh`.

## Reproduced and fixed

| Finding | Reproduction and correction | Regression |
|---|---|---|
| Invented cold support | A correctly signed, committed, fully replayed cryogenic record could set its support to 1 K and report loss falling from 6.836264 kg to zero without a cooler or energy. Certification now pins the structure and sink to the playable contract's 293 K / 3 K boundary. | `server_rejects_committed_forged_cryogenic_proofs` |
| Supercritical liquid relief | A 2 MPa LH2 relief point was accepted even though the model predicts about 46 K, above hydrogen's 33.145 K critical temperature. Tank validation now rejects non-finite, nonpositive and critical/supercritical relief isotherms. | `a_supercritical_relief_point_is_not_a_liquid_tank` |
| Signed zero lost in JSON | Canonical FDR and receipt bytes distinguish `-0` from `+0`; JavaScript re-serialization erased that bit, breaking the pilot signature or server receipt. Receipt attachment and verifier export preserve signed zero; the authority JSON writer does too. | `recorder.test.js`, `signed_zero_survives_json_transport`, native/workerd browser authority gate with a real `-0` maneuver and re-import |
| Stale browser verdict and rating | An old replay, file read, public fetch, player GET or authenticated receipt could finish after newer state and overwrite it. Delivering a genuine old 101 receipt after later ranked flights rolled the profile from 1224.252349 back to 1200.881348. Operations now have generation/revision guards; ranked certificates are retained without blindly applying delayed, duplicate or Practice ratings, retries retain the original revision, and a fresh player sync follows acceptance. Editing clears the displayed verdict, and the debrief shows the actual document being verified. | `tests/browser/authority.mjs` reverses syncs, releases old workers/fetches, overlaps real ranked submissions on both adapters, and simulates an intervening snapshot before a lost-response retry |
| Reopened leaderboard stuck loading | A queued close event could invalidate the fresh request started by an immediately reopened dialog, leaving it loading indefinitely. Old close events no longer cancel an open dialog. | `tests/browser/authority.mjs` closes and reopens before the close event is delivered |
| Assembly snapshot and rejected edits | Relief pressure was missing from the worker snapshot. Some invalid edits also mutated a stage before rebuild failed, or accepted an invalid relief point/non-finite mass. Snapshots now include relief, and bridge edits validate a candidate before committing it or clearing a plan. | `assembly-payload.test.js`, `assembly.mjs`, `invalid_stage_edits_are_atomic_and_cannot_poison_the_plan` |
| False content-hash collision | A bare base64url payload and a `#verify=` fragment for the same signed practice flight could be rejected as a collision because storage compared transport bytes. It now compares decoded canonical bodies while still forbidding a different public key from replacing a flight. | `equivalent_payload_encodings_do_not_collide_but_other_keys_do`, both browser authority adapters |
| Counter wraparound and invalid D1 row | At the `u32` limit SQLite truncated its 64-bit attempt counter; D1 also treated an existing zero row as a missing row and issued a new attempt 1. Both adapters now reject invalid or exhausted counters. Ranked-count increments and SQLite reads also fail closed on overflow/invalid values. | `attempt_counter_fails_closed_at_u32_limit`, `ranked_counter_rejects_out_of_range_database_values`, `ranked_counter_overflow_fails_without_rating_or_receipt`, `cloud-concurrency.mjs` |
| Corrupt receipt or public flight | A one-byte SQLite receipt was interpreted as absent: retrying the same ranked flight moved Elo a second time, from 1200.303716 to 1200.600503. Two valid but conflicting same-attempt receipt copies also let a retry and public lookup report different Elo. SQLite now rejects malformed rows; the engine verifies bindings and compares same-attempt copies, and public lookup requires its idempotency row to agree. A missing row is detected on retry when that same attempt remains indexed. | `corrupt_or_mismatched_receipts_cannot_rate_a_retry_twice`, `public_replay_rejects_corrupt_or_mismatched_flight_rows`, D1 receipt fault injection in `cloud-concurrency.mjs` |
| Coerced SQLite index and commitment | A stored mode of 256 wrapped to Ranked (0), so both a corrupt public-flight index and a corrupt commitment could be accepted. SQLite's integer accessors also coerce text and formerly truncated long hashes/keys. Reads now check original numeric types, bounds and exact key/hash lengths before binding them to signed data. | `corrupt_flight_index_cannot_be_truncated_into_a_valid_public_record`, `corrupt_commitment_cannot_be_coerced_into_a_valid_ticket_binding` |
| Invalid stored ratings | SQLite converted non-numeric Elo text to zero, and the in-memory authority could mint a receipt with infinite ratings. SQLite now rejects nonnumeric/nonfinite ratings and the engine requires finite inputs and outputs. | `non_numeric_or_non_finite_ratings_fail_closed`, `non_finite_stored_ratings_never_mint_a_receipt` |
| Noncanonical base64url | A lone zero sextet (e.g. `A`) was decoded as no bytes. Tails of length 1 modulo 4 are now rejected, while standard unpadded encodings still round-trip. | `rejects_impossible_single_sextet_tails` |

## Resolved in v4

The tug's two signed tank volumes used to total **40.475496 m³** against a
catalog **38.6 m³**, because the catalog number was the *usable* volume
(38.548092 m³) read as the whole airframe and then padded 5 % per tank. v4
derives one `TankGeometry` for mass, card, thermal spec and oracle: the airframe
is 39.740301 m³, usable 38.548092 m³, ullage a single shared 3 %.
`oracle_tank_volume_zero_discrepancy` holds the residual to 1e-9 relative and
`tug_geometry_matches_the_airframe_it_is_signed_into` replaces the test that
disclosed the gap. The frozen v1/v2/v3 fixtures keep the old geometry.

Remaining open items are tracked in the v4 plan: oracle 3 (true single-segment
resumption) is not implemented yet, so checkpoints still verify after a full
replay, and scoring re-baselining is in progress. First-attempt commitments
cannot prove that an untrusted client did not simulate earlier. See [thermal.md](thermal.md) and
[server-authority.md](server-authority.md).

## Compatibility and deployment

No FDR or receipt signing layout changed. New verification rules can reject
previously accepted custom v3 thermal records with different boundary
temperatures or supercritical relief settings, even if an old receipt signature
is valid. Standard baseline/card records keep their calculation; pre-v3 records
have no thermal block. Retain an appropriately versioned historical verifier
if the old acceptance behavior is needed, and coordinate browser/authority
rollout. Previously malformed base64url tails are no longer accepted.

Public lookup and retries now return a storage error instead of success when
receipt copies or required idempotency rows are inconsistent; invalid SQLite
index and commitment types also fail closed. Check and repair existing data
from trusted backups before rollout rather than silently treating damage as a
new attempt. The checks cannot reconstruct a lost idempotency row when the old
flight is no longer indexed (or a different record is submitted).

Receipt timestamps are not transaction sequence numbers: they have one-second
resolution and can reflect request start rather than commit order. Browser
revision guards order operations within the current page, and a successful
receipt triggers a fresh player sync, but offline cached receipts and other
tabs/devices can still show a historical snapshot. The player GET has no signed
global revision, so this is not a cross-client linearizability guarantee.

The Cloudflare tests use workerd/Miniflare and disposable test keys; they are
not a production deployment, distributed-systems proof, migration of remote
data or a substitute for operational rate limiting, durable backups and key
management.
